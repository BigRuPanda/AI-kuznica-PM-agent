# Приёмка помощника продакта Softline

Цель — проследить один показатель от уведомления до решения после релиза. Для проверки нужны Node.js 24.5 или новее в ветке 24, pnpm, Python 3.10+ и Docker Compose v2. Для браузерной проверки подойдёт установленный Edge либо Chromium для Playwright. Все команды выполняются из корня проекта. Стенд использует отдельные базы в `var/pilot` и отдельные тома Docker.

## Поднять локальный стенд

```sh
pnpm install --frozen-lockfile
pnpm build
docker compose -f pilot/compose.yaml up -d --wait --wait-timeout 300
pnpm pilot:prepare
pnpm pilot:start
```

Команда запуска печатает ссылку на разбор. Интерфейс приложения открыт на [127.0.0.1:18090](http://127.0.0.1:18090), письма доступны в [Mailpit](http://127.0.0.1:18025). В настоящем локальном [Redmine](https://localhost:18443) подготовлены закрытый проект и фильтруемое поле «Происхождение задачи». Два тестовых логина — `pilot-writer` и `pilot-reader`. Пароли находятся в полях `writerPassword` и `readerPassword` локального файла `var/pilot/access.json`. Этот файл содержит также ключи тестовых пользователей и исключён из Git.

Пилот доверяет локальному удостоверяющему центру Caddy только в процессе Node. Для непосредственного просмотра Redmine браузеру нужен доверенный сертификат из `var/pilot/redmine-ca.pem`; поиск и чтение через интерфейс помощника работают с настройкой доверия приложения. Порт SMTP привязан к loopback; почтовый приёмник сохраняет письма локально. Если Windows запускает другой Python, задайте `PYTHON_BIN` до старта. Остановить контейнеры с сохранением данных можно командой `docker compose -f pilot/compose.yaml stop`.

## Пройти сценарий продакта

1. Откройте письмо на адрес `product@pilot.invalid`, перейдите по ссылке и войдите как `pilot-writer`. В синтетическом кейсе «Пилотный ЛК» базовый CTR на десктопе за 6 июля – 2 августа 2026 года — **224/2800 = 8%**. Две следующие недели дали **28/700 = 4%** и **21/700 = 3%**. На мобильных устройствах показатель остался на уровне **8%**. Повторная загрузка тех же дней сохраняет одну отправку первоначального сигнала.
2. Откройте данные и источники сигнала. Сверьте периоды, сегменты и основания долей. В блоке **«Поиск по интервью»** введите «выбирать рекомендации в кабинете» и нажмите **«Найти выдержки»**. У двух респондентов различается опыт. Укажите, какая гипотеза требует проверки и какую часть воронки имеющиеся сведения позволяют оценить. В разделе **«Источники»** откройте журнал тестового счётчика 78101. Здесь видно, до какой даты дошла загрузка. Кнопка синхронизации повторяет выдачу локального тестового API.
3. Нажмите **«Подготовить задачу по сигналу»**. До записи проверьте заголовок, источник, поле `ai-generated` и текст «Сгенерирована ИИ-помощником.». Подтвердите запись. Во втором профиле браузера войдите как `pilot-reader`, откройте тот же разбор и найдите задачу через **«Только с меткой ai-generated»**. Сверьте номер.
4. В разделе **«Проверка эффекта»** задайте дату выкладки **17.08.2026**, метрику `lk_reco_ctr`, сегмент `desktop`, источник `metrika:78101:lk_reco_ctr`, абсолютную цель **≥ 5%**. База — **06.07–02.08.2026**, контроль — тот же продукт и источник, сегмент `mobile`. До появления данных результат показывает недостаточное покрытие.
5. Во втором терминале выполните `pnpm pilot:recovery` и обновите разбор. За четыре полные недели с 17 августа по 13 сентября факт — **168/2800 = 6%**, контроль — **8%**, вывод — **«Цель достигнута»**. При повторном запуске CLI уже загруженная версия не создаёт новых строк. Для повторения сценария с первоначального состояния используйте автоматическую приёмку ниже: каждый её запуск начинает с чистой БД.

## Воспроизводимые проверки

Для проверки логики на тестовых адаптерах достаточно `pnpm pilot:accept --synthetic`. Для сквозной проверки на подготовленном стенде выполните команды с `--stand` и `--browser-check` из таблицы ниже. Эти прогоны используют синтетические показатели, локальный Redmine и Mailpit.

| Команда | Что проверяет |
|---|---|
| `pnpm test` | Серверные тесты, импорт и миграции, доступ к снимкам, коррекции, доставка, выбор KPI, индексация выдержек и восстановление из копии. |
| `pnpm test:ui` | Сборка и сценарии в браузере с локальным сервером. |
| `pnpm pilot:accept "<путь к исходному ZIP Softline>"` | Дополнительный прогон при наличии архива. Последовательная загрузка v17, числовые эталоны, срезы на дату, две роли, сохранённая ссылка после рестарта и синтетический сценарий. Материалы организатора обрабатываются локально. |
| `pnpm pilot:accept --synthetic --stand var/pilot/access.json` | Новая временная БД, ответы тестового API Метрики, письмо через SMTP в Mailpit, HTTP-вход двух пользователей, запись в настоящий Redmine, поиск по метке и оценка эффекта. |
| `node pilot/start.mjs --browser-check` | Два изолированных браузерных профиля на отдельном локальном сервере (порт 18091), ссылка из письма, подтверждение и поиск задачи коллегой. PM назначает цель в интерфейсе, дожидается загрузки четырёх недель и видит фактические 6%. |
| `node pilot/verify-redmine.mjs` | Потеря ответа после успешного POST в Redmine, последующая сверка и повторное подтверждение. Результат — одна созданная задача агента. Ручная контрольная задача с той же фразой в описании исключена из фильтра. |
| `node scripts/check-synthetic-ctr.mjs --live` | Отдельная пустая БД, вымышленные наблюдения, многошаговая работа Qwen3.7 Flash через MCP и ProxyAPI. Измеряет вызовы и проверяет числа, оговорку о причине и черновик до подтверждения. Требует `PROXYAPI_API_KEY` и сети. |

Для проверки исторического решения на исходном архиве задайте `SIGNAL_RELEASE_ARCHIVE` абсолютным путём к ZIP, включите `SIGNAL_RELEASE_BROWSER=1` и выполните `node --test tests/release-decision.test.mjs`. Без ZIP остаются обязательными синтетические проверки решения по релизу. Результат проверки исходного архива фиксируется отдельно. [Протокол приёмки нового UI](ui-migration-acceptance.md).

Эталон v17 для периода **2–8 ноября** — **0 кликов из 117 визитов**. В срезе на **30 сентября** R-09 и R-10 ещё не произошли. Для Kaspersky и Astra сравнение со всеми доступными неделями даёт соответственно **−32,73%** и **−2,58%**, только с полными неделями — **−33,87%** и **+3,01%**. Тесты отдельно воспроизводят пересмотр сигнала при поправке **70/70 → 100/100** и проверяют адресата уже доставленного сообщения.

## Что зафиксировать на стороне партнёра

Для собственного пилота PM записывает версию приложения, выбранные правила, фактические периоды, номера задач и канал доставки. Время разбора фиксируется от получения письма до решения по черновику; отдельно учитывается время проверки источников. Полезно записать, какое решение PM изменил бы после просмотра доказательств и какие уведомления счёл лишними. Локальные автоматические прогоны подтверждают работоспособность цепочки. Результаты работы с сотрудниками, счётчиком и корпоративной инфраструктурой Softline заполняются при испытании у партнёра.
