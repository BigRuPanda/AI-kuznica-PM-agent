# Полный переход на новый UI с профилями — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Перевести командное приложение, аналитику CSV-релизов и автономный показ на новый UI с профилями, сохранив все 24 сценария из аудита, данные пользователей и ранее выданные ссылки.

**Architecture:** Рабочую ветку создать от локального `main`. Новый UI и профили принять одним слиянием. Из интеграционной ветки переносить законченные сценарии вместе с тестами и адаптировать их к актуальным серверным операциям, типам и правилам доступа. Компоненты и визуальные состояния брать из UI-ветки, расчёты и права проверять на сервере.

**Tech Stack:** Node.js 24, pnpm 11, React 19, TypeScript, esbuild, SQLite (`node:sqlite`), Playwright, Python 3.10+. Для экспорта презентаций используются зависимости и Chromium из интеграционной ветки.

**Spec:** [Матрица требований и приёмки 1–24](#требования-и-приёмка) ниже фиксирует согласованный аудит в репозитории. Дополнительные контракты описаны в [спецификации расследований](../specs/2026-11-27-parallel-investigations-design.md) и [спецификации сценариев чата](../specs/2026-11-27-chat-scenarios-design.md).

## Global Constraints

- Визуальный эталон — `codex/pm-chat-and-investigation-ui@2f7a3c0`. `codex/chat-avatar` указывает на тот же коммит. Сохранить светлую тему по умолчанию, тёмную тему, оба положения меню, компактные панели, мобильное и клавиатурное управление.
- В `#profile` остаются редактирование имени, загрузка и удаление фото JPEG/PNG/WebP до 10 МБ, инициалы, роль и выход. Личные и командные настройки остаются отдельными пунктами навигации. Фото у сообщения определяется по подтверждённому авторству.
- Сохранить роли администратора, участника и жюри, границы личных и командных материалов, пять сценариев чата, черновики по пользователю и беседе, независимый веб-поиск и явное «без интернета». Старые HTTP/MCP-клиенты, прямой Redmine, личные ключи, Telegram и вход по приглашению продолжают работать.
- Соблюдать действующие `DATA_PROFILE=local|configured`, ограничения адресов и SMTP, `LLM_DATA_MODE`, `SOURCE_ARCHIVE_SHA256` и настройки каналов. Профиль пользователя и режим обработки данных — разные настройки. Для обязательных тестов использовать синтетические источники, локальные транспорты и изолированные базы.
- Сохранить идентификаторы аккаунтов, чатов, исходных версий, снимков, задач, диапазонов и публикаций. У старого снимка показывать только то, что можно подтвердить его данными. Переход на новую версию допускает повторный запуск и рестарт в середине фоновой операции.

## Review Focus

1. Два одноимённых участника и старая реплика без ID. Фото появляется только у подтверждённого автора. Приёмка в T04.
2. Повторный импорт той же книги после публикации расчёта. Старая ссылка открывает прежнюю ячейку и значение. Приёмка в T06 и T08.
3. У владельца нет подтверждённого контакта, контакт сменился или провайдер уже мог принять сообщение. Доставка сохраняет адресность и не дублируется. Приёмка в T09 и T10.
4. Две разные структуры наблюдения записаны как `version: 2`. После обновления каждая открывается своим экраном и считается прежним алгоритмом. Приёмка в T13.
5. Перезапуск после подтверждения задачи или во время сборки презентации. Сохраняются один внешний номер на запрос, одна запись на эпизод закрытия и одна версия презентации на запрос. Приёмка в T11 и T16.

## Рабочие задачи

Команды выполнять в отдельной рабочей копии реализации. Перед каждым браузерным прогоном выполнять `pnpm build`, поскольку тестовый сервер раздаёт `dist/`. Для переносимого поведения сначала запускать донорский тест в исходной ревизии. В каждой задаче прогонять указанную в конце команду дважды: после добавления её теста на исходном коде зафиксировать конкретное расхождение, после реализации получить PASS. Если поведение уже есть, достаточно записать успешный контроль и проверить его в сочетании с перенесённой функцией. Донорские файлы тестов, охватывающие несколько задач, переносить по сценариям вместе с их фикстурами; итоговый перечень сверяется в T17. Каждый шаг «зафиксировать» означает добавить в индекс только изменения этой задачи, проверить `git diff --cached --check` и выполнить указанный коммит.
