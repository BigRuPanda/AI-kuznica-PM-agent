# Помощник продакта · первая версия

## Локальный запуск

Рабочее приложение использует React, TypeScript, Node.js 24 и SQLite. Из корня проекта выполните:

```sh
pnpm install --frozen-lockfile
node telegram.mjs init
pnpm build
pnpm start
```

Откройте [приложение](http://127.0.0.1:8090/). При первом запуске сервер загрузит R-001 и R-002 в `var/releases.sqlite`. Постоянный путь к базе можно задать в `DATABASE_URL`. Интерфейс рассчитан на локальную работу, профили «Анна» и «Дмитрий» позволяют проверить общий чат из разных вкладок. Сохранённые расчёты имеют постоянные ссылки и сохраняют версию данных.

В разделе «Релизы» можно загрузить CSV, добавить релиз и выбрать набор событий. Для сверки двух версий одной выгрузки при повторном импорте выберите существующий набор. Поле «Данные полны по» описывает покрытие источника. Для основной метрики учитывается её собственное окно наблюдения. Пример входного файла — [события двух релизов](demo/events.csv). Структура данных и определения описаны в [правилах расчёта](demo/README.md).

Для проверки чата откройте R-001, спросите «Почему упала конверсия?», затем смените профиль и уточните «А сколько компаний было в каждой группе?». В R-002 запросите график медианного времени от выставления счёта до оплаты. Из ответа можно открыть расчёт и сохранить график в именованный дашборд. Для дополнительных метрик доступны количество событий, статистики сумм оплат и длительности между двумя наблюдаемыми событиями (среднее, медиана и 90-й процентиль).

### Подключение модели

Для выбранного Gemini Developer API в корневом `.env` укажите `LLM_BACKEND=gemini`, `LLM_MODEL=gemini-3.5-flash` и вставьте ключ в `LLM_API_KEY`. Сервер вызывает `https://generativelanguage.googleapis.com/v1beta/models/gemini-3.5-flash:generateContent` и передаёт ключ через заголовок `x-goog-api-key`. Параметры модели перечитываются при изменении файла. После ввода ключа обновите страницу и выполните `pnpm model:check` для проверки вызова инструмента. [Справка Google по ключам](https://ai.google.dev/gemini-api/docs/api-key)

Сервер читает настройки из одного `.env` при запуске. После изменения настроек перезапустите сервер. Ключи и файлы учётных данных остаются на сервере.

**Google Cloud с ADC.** Для модели Gemini 3.5 Flash-Lite укажите:

```dotenv
LLM_BACKEND=vertex
LLM_MODEL=gemini-3.5-flash-lite
GOOGLE_CLOUD_PROJECT=ваш-project-id
GOOGLE_CLOUD_LOCATION=global
```

В выбранном проекте должны быть включены биллинг и API `aiplatform.googleapis.com`. Учётной записи требуется разрешение `aiplatform.endpoints.predict` (например, роль `roles/aiplatform.user`). Для локального входа установите Google Cloud CLI и выполните `gcloud auth application-default login`. При необходимости укажите проект квоты командой `gcloud auth application-default set-quota-project PROJECT_ID`. Если администратор уже настроил файл ADC, путь можно указать в `GOOGLE_APPLICATION_CREDENTIALS`. Приложение получает и обновляет OAuth-токен через библиотеку Google. [Модель и регионы](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-5-flash-lite) · [Локальная аутентификация](https://cloud.google.com/docs/authentication/set-up-adc-local-dev-environment)

**Google Cloud Express.** Для Express Mode задайте `LLM_BACKEND=vertex-express`, `LLM_MODEL=gemini-3.5-flash-lite` и Express API key в `LLM_API_KEY`. Сервер отправляет ключ в заголовке на официальный глобальный endpoint. [Документация Express Mode](https://docs.cloud.google.com/gemini-enterprise-agent-platform/reference/express-mode/api-reference)

**Совместимый HTTP API.** Задайте `LLM_BACKEND=api`, `LLM_BASE_URL`, `LLM_MODEL` и ключ провайдера в `LLM_API_KEY`. Базовый URL должен принимать `POST /chat/completions`. Модель и сервер должны поддерживать инструменты, обязательный выбор инструмента и многошаговый диалог с результатами функций. Модели с собственными протоколами требуют отдельного адаптера. Для локальной проверки каждого API выполните `pnpm model:check`. Проверка делает два коротких вызова модели и передаёт результат тестовой функции.

**Локальная сессия Codex.** При `LLM_BACKEND=codex` и пустых настройках HTTP API сервер может воспользоваться уже авторизованным Codex CLI. Для сеанса разрешены аналитические MCP-инструменты текущего релиза, включён режим чтения, отключены shell, приложения и веб-поиск. Этот вариант использовался для сквозной проверки на синтетических данных. Выбор провайдера выполняется в конфигурации.

### Подключение MCP

Из корня проекта в PowerShell можно зарегистрировать локальный сервер командой:

```powershell
codex mcp add releases -- node (Resolve-Path server/mcp.mjs).Path
```

Сервер использует stdio, общую SQLite-базу и операции `list_releases`, `get_release`, `compare_metric`, `breakdown`, `funnel`, `build_chart`, `get_calculation`. Для первичной сверки передайте в `compare_metric` значения `releaseId=R-001`, `day=14`, `metric=0`, `segment=all`. Результат содержит 140/1000 и 110/1000. Ссылка на тот же результат открывается по адресу `/#calc/ID`. Автоматические проверки запускаются командой `pnpm test`.

## Общая конфигурация

Все настройки прототипа находятся в `.env` в корне проекта. В новой копии проекта файл можно создать по пустому шаблону командой `node telegram.mjs init`. Повторный запуск сохраняет введённые значения. Git игнорирует рабочий файл. На хостинге можно задать те же переменные в среде процесса, где они имеют приоритет.

| Поле | Значение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Токен бота из BotFather |
| `TELEGRAM_CHANNEL_ID` | Числовой ID канала для публикаций |
| `TELEGRAM_CHAT_IDS` | Числовые ID чатов через запятую |
| `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL` | Ключ, базовый адрес API и имя модели. Эти поля зарезервированы для подключения LLM |
| `DATABASE_URL`, `APP_BASE_URL` | Строка подключения к базе и адрес приложения для ссылок на релизы. Их можно заполнить при подключении этих компонентов |

## Подключение Telegram

1. Создай бота командой `/newbot` в [BotFather](https://t.me/BotFather). Добавь его в нужные группы с правом писать. Для публикаций в канале дай ему право «Публикация сообщений».
2. Впиши токен и ID в `.env`. Можно указать канал, чаты или оба варианта. Пример списка чатов — `TELEGRAM_CHAT_IDS=-1001234567890,-1009876543210`.
3. Выполни `node telegram.mjs check`. Проверка читает сведения о боте, указанных адресах и его правах. [Telegram Bot API](https://core.telegram.org/bots/api#getchatmember)

## План реализации первого прототипа

Продакт получает сообщение о релизе, открывает страницу с метриками и спрашивает, у каких клиентов произошло изменение. Агент показывает расчёт. Коллега продолжает тот же разговор в Telegram или на сайте. В отчёте команда сохраняет гипотезу и способ её проверить.

Готов [интерактивный макет](prototype/index.html) с двумя релизами. Его можно открыть прямо в браузере или запустить командой `node prototype/serve.mjs` и перейти по локальному адресу, выведенному в терминале. Для просмотра не нужны ключи. Данные для макета пересобираются из CSV командой `node demo/build-dashboard.mjs`. Ответы чата и выбор участков в макете иллюстративны. Утилита Telegram проверяет токен и доступ по ID. Общая серверная история и обмен сообщениями с Telegram входят в план разработки.

### Порядок разработки

Первую рабочую версию собираем по пути «CSV → страница релиза → вопрос → проверяемый ответ». Так аналитический модуль можно проверить на известных числах до подключения внешних сервисов. Рабочее предложение для локального прототипа — React и TypeScript для интерфейса, Node.js для API и фоновой обработки, SQLite для хранения данных. Такой стек позволяет использовать существующие утилиты и запускать проект в одной серверной среде. Настройки всех компонентов читаются на сервере из общего `.env`.

### Интерфейс первой версии

Каждый график сравнивает версии интерфейса. Графитовая линия показывает всех, серая пунктирная — старую версию, бордовая — новую. Кнопки легенды переключают видимость рядов. Фильтр типа клиента действует сразу на все ряды. Подсказка по дате и раскрытый расчёт показывают фактические значения и базу расчёта по версиям. Записи без подтверждённого показа входят в общий ряд, их количество видно отдельно. При отсутствии сведений о версиях график показывает только общий ряд.

В журнале показываем название и дату релиза, основную метрику и состояние наблюдения. Добавление релиза начинается с одной кнопки. Из журнала и из Telegram открывается одна и та же постоянная ссылка на страницу релиза.

Сверху расположены вкладки «Рабочая область» и «Релизы». Первая открывает заглушку с переходом к релизам. Во второй слева находится список релизов, по центру разбор, справа обсуждение. Обе боковые панели сворачиваются и меняют ширину перетаскиванием или стрелками с клавиатуры. При первом входе открывается самый свежий релиз, при повторном — последний выбранный. Прямая ссылка имеет приоритет. На узком экране список, графики и чат открываются по очереди.

Выбран вариант **«Сначала вывод»**. Под выводом расположены графики пяти метрик в постоянном порядке: конверсия оформления в оплату, оплата выставленных счетов за семь суток, сумма оплат, средний чек и своевременные продления. У каждого графика есть подпись по выбранному срезу. Дневная шкала охватывает весь период анализа до даты среза. Значения над графиком всегда сравнивают первые семь суток после включения с семью предшествующими сутками. Под расчётом доступны исходные количества.

Агент выбирает постоянные обводки при первом полном разборе и может оставить выбор пустым. Сохраняются дата, версия данных и основание выбора. Отдельные участки могут появляться и позднее на любом графике. Они относятся к определённым датам и сегменту. Разбираем одновременно величину сдвига и размер выборки, по нажатию показываем объяснение и исходные числа. В макете показаны заранее заданные примеры этих решений.

Тема всегда светлая. Основная поверхность белая, фон чата светло-серый, текст графитовый. Для действий и отметки ключевого вывода используем бордовый `#A20C32`, для декоративных деталей — серый `#A7A8AC`. Эти оттенки взяты из цветового превью официального логотипа. [Фирменные материалы Softline](https://softlinegroup.com/about/)

Предусматриваем состояния «Наблюдение началось», «Предварительные данные» и «Разбор готов». При отсутствии обязательного поля показываем, что именно требуется для расчёта. В состоянии ожидания ответа агента текущий отчёт остаётся доступен.

### Этапы и приёмка

В рабочем приложении агент сможет по запросу продакта предложить новую метрику, которую можно вычислить из доступных данных. Например, для вопроса о скорости оплаты сервер рассчитает медиану времени от выставления счёта до оплаты среди оплаченных счетов. В чате появятся график, формула и количество учтённых счетов. Продакт сможет сохранить график в релиз и объединить несколько таких графиков в дополнительный дашборд для команды.

| Этап | Что реализуем | Как принимаем работу |
| --- | --- | --- |
| 1. Релизы и загрузка | Локальный запуск приложения, хранилище, начальная загрузка двух релизов и CSV-событий. Фиксируем идентификаторы, время включения, аудиторию, целевую метрику и версию набора данных. Добавляем просмотр журнала и ручное создание релиза. | После повторного импорта количество событий прежнее. Ошибка в файле указывает строку и поле. После перезапуска созданный релиз доступен по своей ссылке. |
| 2. Первый расчёт и ранний MCP | Начинаем с конверсии R-001 на CSV. На входе — релиз, метрика, дата среза и фильтры. В результате сохраняем период, исходные количества, сегмент и версию данных. Сразу после проверки конверсии открываем эту же операцию через MCP. Затем добавляем остальные определения метрик и состояния полноты данных. | Получаем одинаковые исходные количества для R-001 при прямом вызове и через MCP. Проверки воспроизводят числа обоих релизов, включая сегменты. На прошлую дату видны только доступные к тому моменту события. |
| 3. Страница релиза | Первый обзор, график с отметкой запуска, дата среза, фильтр сегмента и действие «Показать расчёт». На странице видно, кого учитывали и когда закончится окно наблюдения. | Продакт открывает R-001, видит падение общего показателя и за один переход находит исходные количества для новых и постоянных клиентов. |
| 4. Агент и общая история | Подключаем одну модель через API. Агент умеет сравнивать периоды, запрашивать сегменты и шаги воронки. Вместе с вопросом получает текущий релиз и фильтры. Сохраняем автора, ответ и ссылку на конкретный расчёт. | Первый участник спрашивает «Почему упала конверсия?», второй продолжает с тем же периодом. Если данных мало, агент указывает недостающее поле или дату. Сохранённый ответ открывает расчёт на той версии данных, на которой он был получен. |
| 5. Telegram | Берём токен, канал и разрешённые чаты из `.env`. Публикуем сообщение о запуске и первый полный разбор. Связываем сообщения группы с релизом и поддерживаем продолжение обсуждения с сайта. Сохраняем ID входящих событий и состояние отправки. | На тестовой группе вопрос из Telegram появляется на сайте, а ответ с сайта виден у нужного релиза в группе. Повторная доставка входящего события даёт один ответ. |
| 6. Гипотеза и конкуренты | Продакт может сохранить в отчёте наблюдение, гипотезу, сегмент и метрику успеха. Для сравнения берём один конкретный шаг у конкурента, прикладываем ссылку и дату наблюдения. | По карточке гипотезы коллега может открыть исходный расчёт, проверить внешний источник и понять, какое изменение предлагается испытать. |
| Дополнительные источники, после этапа 2 | Когда есть эталонный расчёт по CSV, подключаем Excel и чтение из аналитической SQL-базы. Эту работу можно вести параллельно со страницей и чатом. По мере появления новых операций открываем через MCP сегменты и сохранённый отчёт. | Одна выборка из CSV, Excel и SQL даёт одинаковые исходные количества при одинаковых фильтрах. Сайт и MCP открывают одну версию расчёта. |
| 7. Совместный запуск | Готовим воспроизводимый запуск локально и на хостинге, постоянное хранилище и доступ для двух участников. Проверяем ссылки из Telegram, перезапуск сервера и поведение при недоступности модели. | Два участника проходят полный сценарий. После перезапуска им доступны прежние релизы, диалоги и расчёты. Сравниваем время ручного разбора и разбора с агентом на одном вопросе. |

### Контрольные сценарии

- **R-001 «Новая форма заказа».** Общая конверсия падает с 14% до 11%. Среди новых клиентов она остаётся 5%, среди постоянных — 20%. Агент показывает, что доля новых клиентов выросла с 40% до 60%, и предлагает следующую проверку.
- **R-002 «Скачать счёт».** На дату запуска 2 ноября виден старт наблюдения. На 16 ноября доступен итог за первую неделю с полным окном оплаты — 80 из 200 счетов до релиза и 110 из 200 после. Агент показывает сегменты и предлагает способ проверить влияние кнопки.
- **Один разговор на релиз.** Два участника начинают разбор в Telegram и продолжают на сайте. История, выбранный релиз и ссылка на расчёт сохраняются. Повторная доставка одного события даёт один ответ.

### Что ещё согласовать

1. **Telegram при нескольких группах.** Предложение — один релиз обсуждается в одной группе из списка в `.env`. Если группа одна, используем её автоматически. Если их несколько, продакт выбирает группу при создании релиза. Связь с релизом определяем по цепочке ответов под исходным сообщением бота. На тестовой группе проверяем, какие реплики между коллегами бот получает с выданными правами.
2. **Результат работы продакта.** К этапу 6 определить, кто публикует гипотезу в отчёте. Рабочий вариант — агент предлагает формулировку, а продакт сохраняет её с выбранным сегментом, метрикой успеха и основанием.
3. **Конкуренты и реальные данные.** На встрече с Softline запросить пример разбора недавнего релиза, выяснить, какой шаг занимает больше всего времени, какие поля и определения метрик доступны и с какими площадками сравнивают продукт. До получения материалов сравниваем один публично наблюдаемый шаг, например получение счёта.
4. **Модель и развёртывание.** К этапу 4 выбрать провайдера и проверить вызовы инструментов на вопросах о сегментах, периодах и пропущенных полях. К общему запуску выбрать хостинг, постоянное хранилище и способ входа. Для локальной проверки используем два тестовых профиля.
5. **Встраивание в аналитику Softline.** На своём графике показываем передачу агенту выбранного периода, сегмента и метрики. Подключение панели к корпоративной системе планируем после уточнения платформы и доступа.
