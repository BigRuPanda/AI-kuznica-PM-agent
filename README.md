# Помощник продакта Softline Store

Командное приложение замечает изменения продуктовых показателей, собирает проверяемый разбор и помогает PM довести решение до бэклога и последующей оценки. Основные разделы — **Обзор**, **Чаты**, **Разборы** и **Источники**. У каждой опубликованной версии есть ссылка. Все числа на карточках рассчитывает сервер.

Для публикации приложения по HTTPS следуйте инструкции [«Хостинг на VPS»](#хостинг-на-vps).

[Локальный пилот и протокол приёмки](submission/pilot.md) — тестовый счётчик Метрики, настоящий Redmine по HTTPS, почтовый приёмник и проверка эффекта релиза по CTR.

На новой установке `DATA_PROFILE=local` выполняет расчёты на сервере и отключает отправку запросов модели. Для разрешённого локального трекера задайте его точный origin в `LOCAL_HTTP_ORIGINS`, для почтового приёмника — пару хост:порт в `LOCAL_SMTP_TARGET`. В пилотном стенде это делает скрипт запуска. Профиль `configured` использует указанные в конфигурации внешние сервисы. Отдельный живой тест Qwen через ProxyAPI создаёт собственное пространство с вымышленными данными.

## Запуск на своём компьютере

Потребуются Node.js 24, pnpm 11 (проверено с 11.25) или совместимая версия и Python 3.10+ со стандартной библиотекой. Python нужен для XLSX, PPTX, ZIP и SMTP. Проверено под Windows; тот же сервер запускается в Linux.

~~~sh
pnpm install --frozen-lockfile
pnpm run setup
pnpm build
pnpm start
~~~

Откройте [локальное приложение](http://127.0.0.1:8090). На форме входа нажмите **«У меня есть приглашение»**. Для первого администратора скопируйте значение `ADMIN_INVITE_KEY` из корневого `.env`. Выберите имя, логин и пароль. Код администратора работает только до регистрации первого администратора. Он может выдать участнику одноразовое приглашение в **Настройки команды → Пригласить участника**. Запасной способ — `pnpm ops invite`.

В меню **Профиль** меняются имя и фото, видна роль и доступен выход. Можно загрузить JPEG, PNG или WebP размером до 10 МБ или удалить фотографию, чтобы снова показывались инициалы. Параметры своих исследований и подключений доступны в **Мои настройки**, общие параметры — в **Настройки команды**.

`pnpm run setup` дополняет единственный `.env`, генерирует случайные приглашения и сохраняет введённые значения. В репозитории лежит только шаблон `.env.example`. При изменениях конфигурации перезапустите сервер. Системные переменные имеют приоритет. При необходимости укажите в `PYTHON_BIN` абсолютный путь к Python. База по умолчанию находится в `var/releases.sqlite`, аккаунты — в соседнем `accounts.sqlite`, копии жюри — в `var/workspaces`. На локальном компьютере достаточно стандартного `BIND_HOST=127.0.0.1`.

Команда `pnpm ops links` показывает в вашем терминале готовую ссылку для регистрации жюри и, до первого входа, ссылку администратора. Передавайте каждую ссылку её получателю.

### Загрузка материалов хакатона

Администратор открывает **Источники**, выбирает оригинальный ZIP или отдельную книгу XLSX / презентацию PPTX и нажимает **«Загрузить и пересчитать»**. Можно использовать CLI:

~~~sh
pnpm ops import "/absolute/path/hackathon.zip"
pnpm ops prepare-demo "/absolute/path/hackathon.zip"
pnpm ops audit
~~~

Первая команда обновляет пространство команды. Вторая явно фиксирует набор материалов, доступный **новым** аккаунтам жюри. Для жюри передайте адрес вида `https://ваш-домен/#join/<DEMO_INVITE_KEY>`, локально — `http://127.0.0.1:8090/#join/<DEMO_INVITE_KEY>`. Эксперт регистрируется один раз. Его переписка, публикации и пробные задачи хранятся в собственной базе. Последующие внутренние загрузки команды автоматически в демо не попадают.

Без архива доступны аккаунты, чаты и архив синтетических релизов. Официальные данные передаются отдельно. Поддержаны листы продаж, справочника, метрик, релизов и бэклога v17, конкурентные книги и слайды, вложенные архивы интервью. Для трёх исходных книг интервью сохраняются безопасные тематические метки и адреса ячеек. Для продаж используются заголовки `week_start, product_family, orders_index, comment` листа «Продажи». Метку неполного периода передавайте в комментарии с указанием «неполная неделя».

Чтобы искать дословные ответы и новые темы, продакт отбирает и обезличивает выдержки локально. Администратор загружает отдельную XLSX через **Источники → Загрузить и пересчитать**. В первых восьми строках листа разместите заголовок **Обезличенная выдержка** и дополнительные колонки **Вопрос**, **Продукт**, **Дата**, **Исходная книга**, **Ячейка источника**. Последнюю пару заполняйте вместе, например `Опрос.xlsx` и `Клиенты!C3`. При пропуске этой пары результат будет содержать адрес ячейки в загруженной книге. В колонках **Проверяемая гипотеза** и **Связь с гипотезой** можно записать оценку аналитика `подтверждает`, `опровергает` или `упоминание`. По умолчанию результат считается упоминанием. При импорте проверяются явные контакты и реквизиты. Ответственность за отбор разрешённого текста, включая свободные имена, остаётся у автора выдержки. Чтобы обновить активный индекс, повторите загрузку под прежним именем, сохранив путь внутри ZIP. Ранее опубликованные снимки сохраняют свои версии и источники.

В разборе откройте **Поиск по интервью**, введите тему или цитату и нажмите **Найти выдержки**. Результат показывает текст, адрес ячейки и указанную аналитиком связь с гипотезой. Поиск работает локально в SQLite FTS5. Срез из **Период расчёта** оставляет датированные выдержки по выбранный день включительно. Воспроизводимая проверка на 1000 синтетических книгах — `node --test tests/research-search.test.mjs`. Тест выводит hit@5 и p95 для 20 размеченных запросов.

### Рабочий сценарий

При появлении сигнала исследование запускается автоматически. На первом экране разбора видны общий вывод и рекомендуемое действие. В «Как проверяли» можно открыть роль, результат, влияние проверки на рекомендацию и сохранённый расчёт. Кнопка «Посмотреть план проверки» позволяет отредактировать шаги и выбрать задачу перед подтверждением в трекере. «Проверить другую версию» создаёт личное поручение. Его можно отдельно опубликовать в командном разборе.

В разделе **Настройки команды → Исследования по сигналам** администратор задаёт режим и максимум одновременных ИИ-проверок (по умолчанию 10 на весь экземпляр). Очередь работает и при закрытых страницах. В режиме «По ролям» аналитик и исследователь могут начать вместе, ведущий получает оба результата, затем подключается рецензент. При сбое у роли видны причина и кнопка **Повторить ИИ-проверку**. Готовые этапы сохраняются. Изменение лимита действует сразу, начатые проверки завершаются. Начальный режим — «По ролям». Доступны также «Только ведущий» и «Ведущий и рецензент». В разделе **Мои настройки** каждый участник может выбрать режим своих поручений. Начальный выбор «Как у команды» наследует режим команды. После обновления очередь подбирает активные разборы, после временной ошибки продолжает работу с незавершённого этапа. В режиме обработки `analysis` с подключённой моделью доступны модельные этапы. При локальной обработке видны серверный расчёт и причина ожидания.

1. Откройте **Обзор** после загрузки. Сервер отдельно проверяет абсолютный порог из справочника для индекса заказов и относительную просадку четырёх полных недель против предыдущих двенадцати. Первый сигнал появляется в обзоре; второе последовательное недельное окно создаёт запись на доставку. Порог меняется в настройках.
2. Откройте сигнал и спросите: «Сравни с контрольным семейством и исключи последнюю неполную неделю». Из сообщения и из карточки можно открыть сохранённый расчёт. Для вопросов о рекомендациях в ЛК доступен CTR с фактическим знаменателем.
3. Закрепите нужные карточки, нажмите **Поделиться**, проверьте получателя и перечень элементов. Коллега откроет опубликованную версию из группового чата. Для нового личного исследования выберите **Разборы → Новый разбор**.
4. В разделе **Задачи и документация** найдите похожие задачи, откройте карточку и подготовьте изменения. Проверьте предпросмотр и подтвердите запись. На вкладке Confluence выберите страницу или создайте новую и укажите номер задачи для взаимных ссылок. Жюри проходит весь сценарий в собственном локальном пространстве.
5. В **Проверка эффекта** укажите подтверждённую дату выкладки и цель. Сервер ждёт четыре полных недели для продукта и контроля. При появлении данных возвращает разбор на решение. Поправки к источникам хранятся с автором и учитываются при следующих ответах.

### Журнал релизов и автономное демо

Откройте **Релизы** в боковом меню. В календаре из загруженных документов можно запланировать оценку релиза. Кнопка **Аналитика по событиям CSV** открывает релизы с дневными метриками, срезами по сегментам и обсуждениями. В списке релизов администратору доступны **Импорт CSV** и **Добавить релиз**. График из обсуждения можно сохранить на именованный дашборд. Ссылки на релиз, расчёт, выделение и материал открываются в рабочем пространстве после входа.

Для автономного показа соберите локальные шрифты командой `pnpm build`, затем запустите `node prototype/serve.mjs` и откройте [демонстрацию релизов](http://127.0.0.1:8085). Прямые ссылки открывают [R-001](http://127.0.0.1:8085/#R-001) и [R-002](http://127.0.0.1:8085/#R-002). Дата и сегмент сохраняются для каждого релиза. Графики, светлая и тёмная темы и демонстрационное обсуждение доступны без подключения к командному API.

### Решение, наблюдение и презентация

После загрузки источников откройте **Обзор → Решение по релизу** или одноимённую ссылку у релиза в журнале. Выберите семейство и релиз, затем заполните поле **Дата среза** и нажмите **Показать на дату**. Ссылки в расчёте открывают строки соответствующих версий источников. Из текущего среза можно перейти в чат разбора и к проверке эффекта.

В разборе откройте **Проверка эффекта**. В обычном пространстве архивный план доступен в подразделе **Наблюдение по архивным источникам**. Можно сохранить условия до выкладки по задаче исходного бэклога, а подтверждённую дату взять из журнала релизов. Кнопка **Рассчитать без сохранения** проверяет результат по выбранной дате с учётом окна и контроля.

Нажмите **Собрать презентацию** в разборе или напишите «Сделай презентацию» в его чате. Готовую версию можно открыть в разделе **Презентации разбора** и скачать в PPTX и PDF. Chromium для PDF входит в образ Docker. При локальном запуске можно задать путь к Chromium или Edge через `PM_BROWSER_PATH`. При недоступной модели сборка использует шаблон и сохранённые данные.

## Выделения на графиках и поручения помощнику

В **Чатах** и в обсуждении разбора можно попросить «Покажи динамику завершения подбора Astra». Мини-график в сообщении открывает увеличенный график, исходные числа и пояснение. На запрос «Проверь воронки сам» агент прикладывает кнопку **Открыть разбор**. Если запросить и график, и исследование, у каждого результата будет своя постоянная ссылка.

Вопрос «почему этот график так скачет?» продолжает обсуждение сохранённого ряда с его датами и сегментом. Фразой «я про график визитов» можно вернуться к ранее показанному графику в этой беседе. Если под описание подходят два графика, агент попросит выбрать. Чтобы обсудить открытый экран, попросите «повтори показатели с экрана».

Для вопроса «какие изменения за два дня?» агент сравнивает два последних завершённых календарных дня по Москве. Можно назвать конкретные даты или попросить «за последние два доступных дня». Ответ показывает значения одного ряда, абсолютную и относительную разницу. Если источник недельный, пропущена дата или расчёт завершился ошибкой, агент начинает ответ с ограничения. Более старые дневные данные помечаются как справочные.

В окне материала доступны **Приложить к сообщению** и **Скопировать ссылку**. На странице конкретного разбора кнопка **Добавить в разбор** закрепляет материал на вашем экране. Чтобы снять закрепление, нажмите **Добавлено · убрать с экрана**. После удаления исходного чата личные закрепления и вложенные графики остаются доступны владельцу. Ссылка продолжает открывать сохранённые даты и версию данных. Для передачи личного материала в групповой чат при отправке подтвердите доступ команды к вложению.

Воронка конфигуратора использует счётчики визитов из версий загруженных документов. В подробностях доступны числители, знаменатели, покрытие, сегменты устройств и адреса строк. Пропуски отмечаются отдельно. После временного сбоя автор поручения может нажать **Продолжить с сохранённого шага**.

На недельном индексе, в архивных дневных графиках и на графиках агрегированных метрик наведите курсор на дату. Вертикальная линия и общая подсказка показывают видимые ряды, значение и разницу с предыдущим календарным периодом. Пропуск разрывает линию. Неполный период помечается отдельно.

- Мышью выберите точку или протяните участок A. Кнопка **Добавить период для сравнения** включает выбор B. Границы каждого периода можно исправить в полях дат.
- На телефоне коснитесь для подсказки, удерживайте и протяните для выбора. С клавиатуры используйте стрелки, Home/End, пробел для точки и Shift со стрелками для интервала.
- **Спросить** прикрепляет выбор к черновику. Только отправка сообщения запускает агента. В истории останется ссылка на исходные даты, ряды и версию. Из архивного графика и сохранённого расчёта откроется личный чат.
- Для A и B показываются покрытие, неполные наблюдения, разница B минус A и изменение к A в процентах, если знаменатель ненулевой. Для продуктов доступны показатели по общим неделям. В архиве конверсия, медиана и P90 пересчитываются на выбранных интервалах из закреплённой версии событий.
- На вопрос «почему здесь?» агент может проверить контроль, соседний период, релизы и исследования. Дополнительные результаты можно добавить в личный вид. Сохранённые черновики, публикации и их получатели показываются в переписке. Подтвердить публикацию или изменение задачи и страницы может владелец соответствующего предпросмотра.

В `LLM_DATA_MODE=analysis` модель работает максимум шесть раундов и получает проверенные агрегаты и релевантные выдержки. Результаты шагов и квитанции хранятся в SQLite. После перезапуска обработчик продолжает незавершённое поручение. Повторная ошибка возвращает отчёт о сделанном. В `selection` сохранён прежний режим выбора карточек с локальной обработкой фактов. Текст вопроса и обычные реплики истории могут передаваться настроенному провайдеру.

Для сопоставления моделей выполните `pnpm agent:eval` или `pnpm agent:eval --model=ИМЯ --input-price=ЦЕНА --output-price=ЦЕНА`. Прогон использует отдельную базу в памяти, синтетические источники и реальные вызовы указанной модели. Наружу задачи не отправляются. JSON содержит результат каждого сценария, операции, время, вызовы, токены и стоимость по заданной цене за миллион. Отсутствующая цена отмечается `null`. Прошлый файл стоимости относится к первоначальному трёхзапросному сценарию.

## Яндекс Метрика

Для отчёта по CTR задайте две метрики API, например `{"id":"lk_reco_ctr","product":"ЛК","numerator":"ym:s:goal123visits","denominator":"ym:s:goal456visits","dimensions":"ym:s:date","unit":"ratio"}`. Подставьте ID целей клика и видимого показа своего счётчика. CTR за период и для интервалов A/B рассчитывается как сумма кликов, делённая на сумму визитов с показом. У отчётов с одной `metric` сохраняется исходное значение. Карточки CTR и охвата предлагают выбрать ряд при неоднозначности, а для графика можно передать `sourceId` и `definitionId` из каталога. В `disjointCounters` перечислите подтверждённые ID счётчиков с непересекающимися аудиториями. Общий ряд `group:<id отчёта>` требует наблюдения каждого счётчика за дату. Дневные наблюдения `ym:s:date`, недельные `ym:s:startOfWeek` и книги Excel хранятся раздельно. При первом запуске каждого пространства индекс метрик восстанавливается из сохранённых документов. Ссылки на сохранённые отчёты открывают снимки с исходными данными.

1. Используйте счётчик, к которому у вашей учётной записи есть доступ на чтение. Подойдёт разрешённый тестовый счётчик. Логин покупателя интернет-магазина предназначен для другого сервиса.
2. Получите OAuth-токен приложения Яндекса с правом `metrika:read`. В `.env` задайте `METRIKA_TOKEN` и `METRIKA_COUNTER_IDS` (один или несколько числовых ID через запятую).
3. Необязательный `METRIKA_REPORTS_JSON` задаёт отчёты. Например, `[{"id":"store_visits","metric":"ym:s:visits","dimensions":"ym:s:date,ym:s:deviceCategory","product":"Store","unit":"visits","date1":"30daysAgo","date2":"yesterday"}]`. Для отчёта по цели используйте фактический ID цели счётчика. Первой группировкой укажите `ym:s:date` или `ym:s:startOfWeek`. Недельная загрузка ждёт завершения воскресенья. Укажите часовой пояс счётчика в `METRIKA_TIME_ZONE`, по умолчанию используется `Europe/Moscow`. Параметр `filters` задаётся отдельно для каждого отчёта.
4. Выполните `pnpm ops check-metrika`, чтобы проверить чтение всех страниц. После перезапуска нажмите **Источники → Синхронизировать Метрику**. Журнал показывает последнюю попытку, успешную загрузку, проверенный период, последнее наблюдение, страницы, строки, задержку источника и долю выборки. Пустой ответ подтверждает проверку периода. После ошибки или перезапуска следующая загрузка догружает пропущенный период и перечитывает окно для поздних поправок. Финансовый индекс из BI поступает через Excel. Для регулярной синхронизации укажите `METRIKA_SYNC_MINUTES` не меньше 5. Значение 0 оставляет ручной запуск.
5. При 401 проверьте токен, при 403 — права именно на указанный счётчик, при 400 — совместимость метрики, группировок и цели. При 429 повторите позже с меньшим периодом. [Авторизация](https://yandex.ru/dev/metrika/ru/intro/authorization) · [API отчётов](https://yandex.ru/dev/metrika/ru/stat/openapi/data_1)

## Подключение Redmine и Confluence

В разделе **Настройки команды → Подключения команды** администратор указывает HTTPS-адрес Redmine и идентификатор проекта. Командная конфигурация Confluence доступна через `POST /api/team/integration-config` и включает адрес, редакцию и ключ пространства. Для Cloud используйте основной адрес сайта, для Data Center сохраните префикс установки (например, `/confluence`). При пустом адресе Redmine используется настроенный Signal Bridge, без него доступен локальный бэклог. Жюри работает в собственном демопространстве. Для взаимных ссылок обе системы должны работать в одном режиме.

1. Запустите `pnpm setup` и перезапустите сервер. Команда создаёт 32-байтный `INTEGRATION_KEY` в серверном `.env`. Он нужен для расшифровки персональных подключений после восстановления базы. Храните резервную копию этого ключа отдельно от SQLite.
2. Для Redmine 5+ включите REST API. Участник вводит свой API-ключ и проверяет доступ к проекту. Для выбора исполнителя требуется чтение участников проекта. Тип задачи, приоритеты и разрешённые переходы приложение запрашивает у Redmine.
3. Для Confluence Data Center участник вводит персональный токен с правами на нужное пространство. Для Cloud зарегистрируйте OAuth 2.0 (3LO) приложение Atlassian и задайте `CONFLUENCE_CLIENT_ID`, `CONFLUENCE_CLIENT_SECRET` и внешний `APP_BASE_URL`. Callback — `/api/integrations/confluence/callback` на этом адресе. Разрешения приложения: `read:confluence-content.all`, `read:confluence-space.summary`, `search:confluence`, `write:confluence-content`, `read:page:confluence`, `write:page:confluence`, `read:space:confluence`. Запрашивается `offline_access` для обновления личного доступа.
4. Для Redmine участник открывает **Мои настройки → Личные подключения**, нажимает **Подключить Redmine**, затем **Проверить доступ**. Здесь же можно заменить или отключить личное подключение. Личный доступ к Confluence настраивается через `POST /api/team/integration-access`. С сервера доступны `pnpm ops check-redmine` и `pnpm ops check-confluence` с персональным ключом приложения в `MCP_ACCESS_TOKEN`. Черновик сохраняет выбранный экземпляр и проект. Для записи в другое назначение создайте новый черновик.
5. При приёмке найдите задачу, измените статус и добавьте комментарий. Если в интерфейсе включена вкладка Confluence, создайте страницу со ссылкой на задачу, затем обновите фрагмент существующей страницы. Проверьте авторство, ссылки и просмотр вторым участником. При конфликте версий проверьте свежий предпросмотр. При неопределённом результате используйте **Сверить результат**. Если запись страницы прошла, а обратная ссылка не сохранилась, кнопка повторяет только работу со ссылкой.

[Redmine Issues](https://www.redmine.org/projects/redmine/wiki/Rest_Issues) · [Confluence Cloud API](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-page/) · [OAuth 2.0](https://developer.atlassian.com/cloud/confluence/oauth-2-3lo-apps/) · [Confluence Data Center API](https://developer.atlassian.com/server/confluence/confluence-rest-api-examples/)

Signal Bridge подключается отдельно. Укажите `SIGNAL_BRIDGE_URL` в серверном `.env`. При `DATA_PROFILE=local` внесите точный origin Bridge в `LOCAL_HTTP_ORIGINS`. Для личной доставки участник подтверждает почту или привязывает Telegram в **Мои настройки → Мои уведомления**. Результаты закрытия задач доступны в разделе **База знаний**. Bridge можно запустить и без сайта. [Запуск и проверка Signal Bridge](integrations/signal-bridge/README.md).

## Модель, Telegram и SMTP

**Модель.** Проект использует Qwen3.7 Flash через ProxyAPI. Для подключения укажите в корневом `.env`:

~~~dotenv
DATA_PROFILE=configured
LLM_BACKEND=proxyapi
LLM_MODEL=qwen/qwen3.7-flash
~~~

После `pnpm run setup` выполните `pnpm model:key` в своём терминале. Команда принимает токен со скрытым вводом и записывает его в `PROXYAPI_API_KEY` локального `.env`. На сервере ключ также можно задать через переменную окружения. Запустите `pnpm model:check`, чтобы проверить вызов инструмента и чтение его результата на тестовом числе. Приложение отправляет запросы на `https://api.proxyapi.ru/v1/chat/completions`. [Карточка модели и пример запроса](https://proxyapi.ru/models/qwen/qwen3.7-flash)

Альтернативные значения `LLM_BACKEND` — `gemini`, `vertex`, `vertex-express` и `api`. Для этих провайдеров укажите соответствующий `LLM_MODEL`, для ключевой авторизации — `LLM_API_KEY`, для совместимого API — `LLM_BASE_URL`. Для Vertex ADC используются `GOOGLE_CLOUD_PROJECT` и `GOOGLE_CLOUD_LOCATION`. В обоих режимах работы с данными агент может ответить текстом, уточнить вопрос или вызвать расчёт. Ему доступны до 16 предыдущих реплик этой беседы. В `LLM_DATA_MODE=selection` прежние аналитические ответы представлены названиями продуктов и типами карточек, а числовой ответ и ссылки формирует сервер. В `analysis` модель также получает отобранные факты и формулирует вывод. Без модели остаются простые диалоговые ответы и локальные расчёты.

**Telegram.** Создайте бота через BotFather, добавьте его в нужную группу. Укажите `TELEGRAM_BOT_TOKEN`, список разрешённых групп в `TELEGRAM_CHAT_IDS`, при необходимости `TELEGRAM_CHANNEL_ID` и случайный `TELEGRAM_WEBHOOK_SECRET`. `pnpm ops check-telegram` проверяет бота. На VPS задайте внешний HTTPS-адрес в `APP_BASE_URL` и выполните `pnpm ops register-webhook`. Откройте **Мои настройки → Привязать Telegram** и отправьте выданную команду в личку боту. В группе используйте `/ask вопрос` или отвечайте на сообщение бота. Входящие сообщения требуют доступного Telegram HTTPS webhook. [Telegram Bot API](https://core.telegram.org/bots/api)

**Почта.** Укажите `SMTP_HOST`, `SMTP_PORT`, `SMTP_TLS=starttls` (обычно 587) или `implicit` (обычно 465), `SMTP_FROM`, `SMTP_TO`, при необходимости логин и пароль приложения. `pnpm ops check-smtp` проверяет соединение и вход без письма. `pnpm ops test-smtp` отправляет одно тестовое письмо. Для фоновой доставки задайте `NOTIFICATIONS_ENABLED=true`. `NOTIFICATION_CHANNELS` позволяет выбрать `smtp`, `telegram` или оба канала через запятую. По умолчанию выбраны оба. В разделе **Настройки команды → Доставка уведомлений** показаны отключённые каналы и фактическое число записей по каждому состоянию. Неопределённая доставка требует сверки. Дубли защищены ключом сигнала и канала.

## Хостинг на VPS

Схема для одного сервера с Ubuntu 24.04 LTS. Docker Compose собирает приложение вместе с Node.js и Python. Caddy принимает запросы на портах 80 и 443, выдаёт и обновляет TLS-сертификат. Приложение слушает порт 8090 внутри сети Compose. Том `pmdata` хранит SQLite с аккаунтами, расчётами и пространствами жюри при пересоздании контейнеров. [Автоматический HTTPS в Caddy](https://caddyserver.com/docs/automatic-https)

В командах замените `ubuntu` на пользователя VPS с правами `sudo`, `203.0.113.10` на публичный IP сервера, а `pm.example.com` на свой поддомен.

### 1. Подготовьте сервер и DNS

1. Создайте VPS с публичным IPv4 и доступом по SSH. Для небольшого командного стенда можно начать с 2 vCPU, 2 ГБ RAM и 20 ГБ диска.
2. В панели хостинга разрешите входящий TCP-трафик на 80 и 443 и доступ к SSH. Оставьте 80 и 443 свободными для Caddy.
3. У DNS-провайдера создайте запись `A` для `pm.example.com` со значением публичного IPv4. Добавляйте `AAAA`, только если у VPS есть рабочий публичный IPv6. Проверьте, что ваш поддомен уже возвращает IP сервера. [Проверка DNS и портов для Caddy](https://caddyserver.com/docs/troubleshooting)

Подключитесь по SSH с компьютера.

~~~sh
ssh ubuntu@203.0.113.10
~~~

На VPS установите Docker Engine с плагином Docker Compose по инструкции Docker для Ubuntu. Если хостер уже подготовил образ с Docker, сразу проверьте версии. [Установка Docker из apt-репозитория](https://docs.docker.com/engine/install/ubuntu/#install-using-the-apt-repository)

~~~sh
sudo apt update
sudo apt install -y git curl openssl nano
sudo docker version
sudo docker compose version
getent ahostsv4 pm.example.com
~~~

### 2. Перенесите код на VPS

Если нужная версия уже есть на GitHub, выполните на VPS следующие команды.

~~~sh
git clone https://github.com/BigRuPanda/AI-kuznica-PM-agent.git "$HOME/ai-pm-agent"
cd "$HOME/ai-pm-agent"
~~~

Если нужные изменения пока только на вашем компьютере, передайте исходники через `scp`. В PowerShell откройте корень проекта и выполните команды ниже. В архив попадут перечисленные исходники, включая новые файлы. Корневые `.env`, `var/` и `node_modules/` остаются на компьютере.

~~~powershell
$archive = Join-Path $env:TEMP 'pm-agent-source.tar.gz'
tar.exe -czf $archive .dockerignore .env.example .gitignore Caddyfile compose.yaml Dockerfile package.json pnpm-lock.yaml pnpm-workspace.yaml README.md telegram.mjs tsconfig.json demo prototype scripts server tests web
tar.exe -tzf $archive
scp $archive ubuntu@203.0.113.10:pm-agent-source.tar.gz
~~~

На VPS распакуйте архив в новый каталог и перейдите в него.

~~~sh
mkdir "$HOME/ai-pm-agent"
cd "$HOME/ai-pm-agent"
tar -xzf "$HOME/pm-agent-source.tar.gz"
~~~

### 3. Настройте `.env` и запустите приложение

При первом развёртывании выполните в каталоге проекта на VPS следующие команды.

~~~sh
install -m 600 .env.example .env
nano .env
~~~

В `.env` замените значения этих строк. Вызовите `openssl rand -hex 32` дважды и вставьте разные результаты в поля приглашений. Если стенд нужен только команде, оставьте `DEMO_INVITE_KEY` пустым.

~~~dotenv
SITE_DOMAIN=pm.example.com
APP_BASE_URL=https://pm.example.com
ADMIN_INVITE_KEY=ВСТАВЬТЕ_ПЕРВЫЙ_СЛУЧАЙНЫЙ_КОД
DEMO_INVITE_KEY=ВСТАВЬТЕ_ВТОРОЙ_СЛУЧАЙНЫЙ_КОД
NOTIFICATIONS_ENABLED=false
~~~

`SITE_DOMAIN` содержит только имя хоста, а `APP_BASE_URL` — HTTPS-адрес этого же хоста без завершающего `/`. Compose задаёт `DATABASE_URL=/app/var/releases.sqlite`, `BIND_HOST=0.0.0.0` и `PORT=8090` внутри контейнера.

Ключ модели можно добавить после первого запуска. Укажите `LLM_BACKEND`, доступную вашему аккаунту модель в `LLM_MODEL` и параметры выбранного провайдера из раздела [«Модель, Telegram и SMTP»](#модель-telegram-и-smtp). Для Vertex с файлом ADC путь `GOOGLE_APPLICATION_CREDENTIALS` должен быть доступен внутри контейнера. После изменения `.env` примените его командой `sudo docker compose up -d`.

~~~sh
sudo docker compose config --quiet
sudo docker compose up -d --build
sudo docker compose ps
curl --fail --show-error --silent https://pm.example.com/health
~~~

В `docker compose ps` у `app` должно появиться состояние `healthy`, а `/health` должен вернуть `{"ok":true}`. На первый выпуск сертификата может потребоваться несколько минут. После проверки HTTPS откройте `https://pm.example.com` в браузере.

### 4. Создайте аккаунт и подготовьте стенд для жюри

Получите приглашения в SSH-сессии и откройте ссылку первого администратора. Зарегистрируйтесь и проверьте вход. Команда показывает ссылку жюри, если задан `DEMO_INVITE_KEY`. Ссылка администратора доступна до регистрации первого администратора.

~~~sh
sudo docker compose exec app node scripts/ops.mjs links
~~~

При подключённой модели проверьте реальный вызов инструмента, затем задайте вопрос в чате. Проверка делает запрос к провайдеру.

~~~sh
sudo docker compose exec app node scripts/check-model.mjs
~~~

Через **Источники** можно загрузить материалы в пространство команды. Если жюри должно увидеть конкурсные материалы, подготовьте отдельный демонабор до передачи ссылки. Например, если `hackathon.zip` уже загружен в домашний каталог VPS, выполните на сервере эти команды.

~~~sh
sudo docker compose cp "$HOME/hackathon.zip" app:/tmp/hackathon.zip
sudo docker compose exec --user root app chown node:node /tmp/hackathon.zip
sudo docker compose exec app node scripts/ops.mjs prepare-demo /tmp/hackathon.zip
sudo docker compose exec app rm /tmp/hackathon.zip
~~~

`prepare-demo` импортирует материалы в команду и фиксирует набор для новых аккаунтов жюри. Откройте ссылку жюри в приватном окне, чтобы проверить регистрацию и состав демонабора в отдельном пространстве.

### 5. Сохраните данные перед обновлением

Команда `backup` снимает копии SQLite и проверяет их целостность. На время копирования остановите приложение и фоновые задачи. Выполняйте команды из каталога проекта на VPS.

~~~sh
backup_dir="$HOME/pm-backups"
install -d -m 700 "$backup_dir"
umask 077
sudo docker compose stop caddy app &&
  sudo docker compose run --rm --no-deps -T app node scripts/ops.mjs backup
~~~

Подставьте имя каталога, которое команда вывела после `/app/var/backups/`. Архив содержит данные команды и жюри. Скопируйте его с VPS в своё хранилище резервных копий. Для восстановления на новом сервере сохраните `.env` отдельно в хранилище секретов.

~~~sh
snapshot='ИМЯ-КАТАЛОГА-ИЗ-ВЫВОДА'
archive="$backup_dir/$snapshot.tar.gz"
sudo docker compose run --rm --no-deps -T app tar -C "/app/var/backups/$snapshot" \
  --exclude='*-wal' --exclude='*-shm' -czf - . > "$archive" &&
  tar -tzf "$archive" &&
  sudo docker compose up -d
~~~

Для обновления версии из GitHub выполните команды ниже. При переносе по `scp` распакуйте новую версию в отдельный каталог и перенесите туда серверный `.env` с правами `600`. Из нового каталога выполните сборку и проверку `/health` теми же командами. Имя проекта Compose `softline-pm` должно совпадать, чтобы использовать прежний том.

~~~sh
git pull --ff-only
sudo docker compose up -d --build
curl --fail --show-error --silent https://pm.example.com/health
~~~

Для восстановления на том же VPS подставьте путь к своему архиву. Процедура сохраняет прежние файлы базы и пространства в каталоге `.before-restore-*` внутри тома, затем запускает приложение со снимком.

~~~sh
archive="$HOME/pm-backups/ИМЯ-СНИМКА.tar.gz"
tar -tzf "$archive" &&
  sudo docker compose stop caddy app &&
  sudo docker compose run --rm --no-deps -T --user root app sh -ec '
    base=/app/var
    incoming=$(mktemp -d "$base/.restore-XXXXXX")
    tar -xzf - -C "$incoming"
    test -f "$incoming/releases.sqlite"
    test -f "$incoming/accounts.sqlite"
    chown -R node:node "$incoming"

    old=$(mktemp -d "$base/.before-restore-XXXXXX")
    for item in "$base"/*.sqlite "$base"/*.sqlite-wal "$base"/*.sqlite-shm "$base/workspaces"; do
      if [ -e "$item" ]; then mv "$item" "$old/"; fi
    done
    mv "$incoming/releases.sqlite" "$incoming/accounts.sqlite" "$base/"
    if [ -d "$incoming/workspaces" ]; then mv "$incoming/workspaces" "$base/"; fi
    rmdir "$incoming"
    printf "Предыдущие данные сохранены в %s\n" "$old"
  ' < "$archive" &&
  sudo docker compose up -d
~~~

После восстановления войдите под прежней учётной записью и откройте сохранённую ссылку на расчёт. Для обычной остановки используйте `sudo docker compose stop`. Команда `docker compose down -v` удаляет тома, включая данные приложения. [Удаление томов в Docker Compose](https://docs.docker.com/reference/cli/docker/compose/down/)

### Если стенд не открывается

~~~sh
sudo docker compose ps -a
sudo docker compose logs --tail 100 app caddy
~~~

| Симптом | Что проверить |
| --- | --- |
| Caddy не получил сертификат | DNS `A` и `AAAA`, доступность 80 и 443 из интернета, сообщения ACME в журнале Caddy. |
| `app` завершился или `unhealthy` | Журнал `app` и значение `APP_BASE_URL` в `.env`. Если изменили `.env`, повторите `sudo docker compose up -d`. |
| HTTP 403 «Неизвестный адрес стенда» | Откройте домен из `APP_BASE_URL`. Он должен совпадать с `SITE_DOMAIN`. |
| Сайт открывается, а проверка модели падает | Проверьте параметры `LLM_*`, доступность модели для ключа и исходящий HTTPS с VPS. |

## Приёмка, экономика и конкурсная поставка

`pnpm build` проверяет TypeScript и собирает интерфейс. `pnpm test` запускает регрессию прежнего прототипа и проверки новой версии: последовательный недельный импорт, частичное покрытие, защита от дублей, версии расчётов, контроль эффекта, два участника, изоляция жюри, перезапуск, совпадение HTTP/MCP и контракты адаптеров. Нужен доступ к localhost. Проверки реальных Метрики, Redmine и Confluence выполняются отдельно после внесения реквизитов.

Браузерная приёмка запускается командой `pnpm test:ui`. Тест собирает приложение, открывает его в Chromium на localhost и создаёт временное пространство с администратором, участником и жюри. Для установки браузера выполните `pnpm exec playwright install chromium`. Под Windows тест также поддерживает установленный Edge. Переменная `PM_BROWSER_PATH` позволяет указать исполняемый файл. Графики, публикации, демозадачи и переходы по старым ссылкам проверяются через работающий сервер. Ответы модели задаёт тестовый адаптер.

После обновления проверьте `/health`, войдите по ранее сохранённой ссылке на расчёт и откройте закреплённый материал с вложенным графиком. При откате используйте ревизию приложения и снимок SQLite, сохранённые перед обновлением.

Приёмка обновления использует три независимых набора SQLite из `scripts/ui-migration-fixtures.mjs`. Передайте каталог наборов через `PM_MIGRATION_FIXTURES` и запустите `node --test tests/ui-migration-upgrade.test.mjs`. [Протокол приёмки нового UI](submission/ui-migration-acceptance.md).

`pnpm ops cost` формирует `var/cost-per-request.csv` из записанных вызовов модели. Заполните цены на миллион токенов в `PRICE_INPUT_MILLION` и `PRICE_OUTPUT_MILLION`, а также месячную инфраструктуру и объём запросов в `MONTHLY_INFRA_COST`, `MONTHLY_REQUESTS`. Стоимость запроса — сумма входных и выходных токенов по тарифу плюс месячная инфраструктура, делённая на число запросов. Пустые тарифы дают пустые поля. Итоги переносятся в шаблон организатора.

**Ранее созданная база** зафиксирована отдельным начальным коммитом: синтетические R-001/R-002, React-интерфейс релизов, CSV-импорт, SQLite, вычисление метрик, stdio MCP, история чата релиза и адаптеры модели. Командные аккаунты и пространства, импорт материалов, самостоятельное обнаружение сигналов, разборы, публикации, мониторинг, удалённый MCP и новые коннекторы добавлены поверх этой базы. Конкурсные книги, локальные аккаунты, реквизиты, внутренние видео и базы в публичную историю не включаются.

## Проверка источников из чата

В «Источниках» нажмите название книги, выберите строку и «Проверить ссылку из …». Введите утверждение, которое хотите сверить. В чате появятся ссылка на ячейку в конкретной версии книги, дата чтения и ссылка на публичную страницу. Можно также вставить URL непосредственно в личный или командный чат. Чтение поддерживает публичный HTML без авторизации. Текстовые ссылки и кликабельные подписи Excel сохраняются вместе с координатой. Для старых книг, в которых прежде сохранилась только подпись, повторите загрузку исходного файла.

Для общего поиска включите «Поиск в интернете» или напишите «Найди в интернете …». В профиле \`configured\` заполните \`YANDEX_SEARCH_FOLDER_ID\` и \`YANDEX_SEARCH_API_KEY\` для Yandex Search API. Сеть получает поисковую фразу. Указание «без интернета» отключает поиск для сообщения. Ссылки Яндекса сопровождают выдержки из выдачи. Прямое чтение страницы и чтение ссылки из книги работают без ключа Яндекса. Для сверки актуальной цены можно указать продавца и артикул из исследования. Проверка сопоставляет артикул, редакцию, срок, объём и единицу цены.

В профиле \`local\` доступны книги и сохранённые версии. В \`selection\` чат показывает выдержки без отправки их модели. В \`analysis\` настроенная модель может сверить утверждение с содержимым публичной страницы. Обработка HTML и XLSX использует Python 3; путь задаётся в \`PYTHON_BIN\`. Формат экспорта \`pnpm ops cost\` включает \`web_requests\` и \`web_cost\`. Для расчёта введите цену одного вызова в \`PRICE_WEB_REQUEST\`. Повторное чтение сохранённого шага расхода не создаёт.

Для пространства организатора можно указать \`SOURCE_ARCHIVE_SHA256\` и отдельный \`DATABASE_URL\`. Первую загрузку выполняют с исходным ZIP. Для обновления книги администратор выбирает XLSX, указывает происхождение, согласует версию и загружает её. У документов с несколькими версиями есть история с доступом к прежним ячейкам. В обычных пространствах действуют существующие правила обновления исследований.

В MCP операции \`knowledge-sources\`, \`knowledge-source\` и \`source_value\` возвращают версии и строки. \`read_public_page\` принимает либо \`url\`, либо \`version\` и \`loc\`. В Telegram рядом с ответом приходят адреса использованных источников.
